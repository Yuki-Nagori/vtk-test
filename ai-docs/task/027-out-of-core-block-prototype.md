## 目标与背景

025 的流式方案是顺序扫描整个资产：1 亿四面体切面 1.76 s，3 亿 5.7 s，10 亿 31.2 s，延迟随总单元数线性增长，无法交互拖动切面。用户已批准单机 out-of-core 架构（2026-10-24 11:30 UTC+8），要求先做最小原型：

- 用 1 亿单元合成四面体网格，实测切面拖动时的粗显示延迟、松手后的精细延迟，以及内存占用。
- 目标：拖动粗显示 < 300 ms，精细 < 1 s。
- 达标后再铺开到应用；不达标就停下汇报数据和原因。
- 无 GPU，无法实测帧率；本任务只测几何计算延迟，不含渲染。

- 基准：`scale_bench` 不改，新增示例 `ooc_bench`，测 1 亿单元的分块耗时、文件大小、粗/精细延迟（冷缓存、热缓存、预算受限）、峰值 RSS，以及读调用次数、读取字节数、打开文件数、写调用次数。

## Windows IO 设计（用户 11:35 UTC+8 要求）

Windows 是主力平台，打开文件、元数据、小块读写和 Defender 扫描都慢，格式和调度按“少 IO 次数”设计：

- 单个大资产文件：`头 16 B | 单元段（按 Morton 序） | 表面段（连续） | zstd 块表 | 尾 32 B`。整个网格只打开一次文件，不产生小文件。
- 打开：一次读尾部 1 MiB 窗口（块表通常就在其中），再一次读整个表面段。实测 1 亿单元打开 = 2 次读调用、5.8 MiB。
- 块按 k-d 叶子的 Morton 序写入：空间相邻的块在文件里相邻，一个切面命中的块大多连续。
- 读取合并：缓存未命中的块按偏移排序，间隔 ≤ 1 MiB 且合并后 ≤ 64 MiB 的相邻块合成一次读；各段并行读、并行解压。实测 1 亿单元冷切面命中 102 块只需 28 次读调用（平均每次约 6 MiB）。
- 定位读：Unix 用 `read_exact_at`，Windows 用 `seek_read` 循环，不需要锁、不改共享文件位置。
- 写入：8 MiB `BufWriter` 顺序写，单元段按 Morton 序经重排缓冲写出；不 seek 回写头部（块表和尾部最后追加），只在结束时 `sync_all` 一次并 rename。实测 1 亿单元 0.84 GiB 共 129 次写调用。
- 基准报告读调用、读字节、打开文件数、写调用。

mmap（`CreateFileMapping` / `MapViewOfFile`）暂不采用：需要 `unsafe` 和新依赖（`memmap2`），工作区禁止 `unsafe_code`，这属于依赖 / 架构决策，交用户决定。合并读已经把读调用压到每次数 MiB 级，mmap 的预期收益主要是省掉一次内核到用户态拷贝，以及由 OS 管理页缓存；在 Windows 上实测前收益不确定。

Windows 上仍需实测（盒子是 Linux，以下未验证）：

- 打开 1 次文件 + 2 次读的实际耗时（含 Defender 首次扫描大文件的开销）。
- 冷磁盘（未进页缓存）下合并读的吞吐与延迟；盒子无 root，无法清页缓存，`posix_fadvise(DONTNEED)` 前后 `cat` 耗时无差异，无法判断冷读。
- `seek_read` 路径的正确性：盒子无 Windows 目标与 mingw，`cfg(windows)` 分支未编译过；nightly Windows 任务会首次编译并运行小规模基准。
- 写入 0.84 GiB 时 Defender 实时扫描对构建耗时的影响。

| 日期 | 环境 / 命令或场景 | 预期 | 实际结果 / 证据 |

| 2026-10-24 | `cargo test -p panta-mesh --lib chunked`（7 项） | 顺序 / ID / 覆盖完整；精细切面与 `section_surface` 位级一致；质量与 `tet_quality` 一致；缓存预算、合并读、预取、损坏 / 截断拒绝、取消 | 通过 |

| 2026-10-24 | 同上，预算 256 MiB（`--reuse`） | 预算受限时仍达标 | 达标，见下表 |

1 亿单元（99,488,250 四面体、16,777,216 节点）构建：13.4 s，512 块，文件 0.84 GiB，写调用 129 次，打开文件 1 个，峰值 RSS 1.8 GiB（主要是每单元 16 B 的质心 / ID 数组）。打开：约 95 ms，读调用 2 次（5.8 MiB），常驻索引 + 表面约 61 MiB。

切面从 0.30 拖到 0.70（每步 1%，每步间隔 16 ms 模拟拖动，后台预取下一位置）。“冷缓存”指块不在 LRU，需要读取并解压；文件刚写完，可能仍在 OS 页缓存。下表取 `MALLOC_ARENA_MAX=2` 下修复后的一轮。

| 平面 | 预算 | 粗级别 p50 / p95 / max | 冷精细（命中块、读调用、读 MiB） | 松手精细 | 逐步精细 p50 / max | 峰值 RSS |
|---|---|---|---|---|---|---|
| 斜面 [0.3, 0.2, 1] | 1024 MiB | 4.5 / 10.3 / 12.8 ms | 304 ms（102 块，28 次，173 MiB） | 96 ms | 105 / 170 ms | 2.0 GiB |
| 轴向 z | 1024 MiB | 3.0 / 22.3 / 23.9 ms | 228 ms（128 块，32 次，217 MiB） | 76 ms | 67 / 166 ms | 2.4 GiB |
| 斜面 | 256 MiB | 10.3 / 14.4 / 16.2 ms | 364 ms（30 次） | 227 ms | 245 / 316 ms | 1.35 GiB |
| 轴向 z | 256 MiB | 8.4 / 13.0 / 14.0 ms | 270 ms（36 次） | 136 ms | 140 / 284 ms | 1.31 GiB |

所有轮次（含首轮未修复内存问题时）粗级别最大 90 ms，精细最大 496 ms，都在目标内。质量统计全量 1 亿单元：首次 2.2–2.9 s（19–25 次读，860 MiB），之后走缓存 < 0.1 ms。粗级别最多约 9.7 万三角形，精细约 90–117 万三角形。

内存：首轮发现峰值 RSS 与预算无关（预算 1 GiB 和 256 MiB 都约 2.75 GiB），原因有两个，已修复：

1. 精细切面和预取一次取全部命中块（100+ 块约 0.6–0.8 GiB 解压数据），绕过了预算。改为按预算一半分批取块，预取量也封顶为预算一半。
2. glibc 每线程 malloc arena 保留已释放内存，`MALLOC_ARENA_MAX=2` 下降低约 0.7 GiB。应用里是否设置 arena 上限（或换分配器）在铺开时决定；Windows 堆行为不同，需在 Windows 上实测。

修复后峰值 ≈ 预算 + 约 1.1 GiB 固定开销（结果缓存上限 256 MiB、命中块的压缩读缓冲、输出网格及其拷贝、常驻索引 61 MiB、分配器保留）。铺开时把结果缓存上限并入总预算，进一步收紧。

GUI / GPU 相关未验证：无 GPU，未测渲染帧率与上传耗时；粗级别 → 精细替换的视觉效果需要 GUI 验证。

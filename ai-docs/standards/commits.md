# Commit 规范与变更一致性

更新日期：2026-09-16。以下是项目约定，不依赖特定 Git 客户端，也不意味着当前已配置 hooks 或 CI 自动门禁。

## 一个 commit 是一个可验证的行为单元

每次 commit 表达一个清楚的目的，包含实现该目的所需的代码、测试、构建/配置、锁文件、文档和 task 更新。不得提交已知损坏的中间状态，再期待下一个 commit 修好；仅在工作区探索的内容整理为一致状态后再提交。

“一致”不要求一个 commit 完成整个 task。可按可用的纵向小步骤提交，每一步都能在其前置提交基础上构建并验证，当前已有功能继续成立。计划中的功能尚未实现时，不添加未使用的占位实现来凑目录，不把缺失能力标成完成。

跨语言签名、schema 或构建入口发生变更时，同一 commit 更新所有本仓库消费者、生成输入和相应验证。生成产物按仓库规范处理，不因签名变化就把构建目录内容加入 Git。外部仓库无法同步时记录版本要求并明确拒绝不支持组合，不擅自留下兼容兜底。

## 每次提交前的一致性检查

1. **行为**：代码完成提交标题描述的结果；修复不破坏已有受支持行为，新增错误路径可解释。
2. **引用与清理**：替换实现时同步移除旧代码、调用点、依赖、配置、资源和失效文档；必要兼容遵循 [生命周期规范](code-lifecycle.md)。
3. **验证**：在实际提交内容对应的状态执行适当检查并记录结果。不能仅依靠未提交文件让测试通过；部分暂存时核对提交是否自洽，必要时在隔离位置验证，不扰动其他工作。
4. **文档与任务**：更新受影响的接口/使用说明和相关 task 工作记录、检查项与证据；索引中的状态、依赖或标题发生变化时在同一 commit 同步。
5. **提交边界**：检查最终暂存 diff，无无关改动、产物或临时备份。保留他人已有更改和暂存状态，不使用整仓暂存或回滚掩盖范围不明的问题。

每次 commit 都要有 task 关联与本次进展记录。状态没变时无需为制造 diff 重写索引，但必须确认 task 与索引一致。文档、构建、测试和清理提交也适用；没有运行入口时记录适用的文档/静态检查，不伪造应用测试。

## Task 状态与工作记录

- 第一次计划提交可保持 draft/planned/ready；开始实现的提交更新为 in-progress。
- 中间提交记录本次完成、验证和剩余工作，仅勾选已有证据的验收项。实际阻塞写 blocked 及解除条件。
- 最后完成提交同时补齐完成摘要、验证证据和索引 done；不能只改索引或只在提交消息中说完成。
- 一次 task 可有多个 commit；一个 commit 原则上属于一个主 task。不可分割的跨任务改动须列出全部关联任务及原因，不能用它聚合无关功能。
- 提交消息引用 task 编号；task 不要求填写当前 commit 的 hash，避免自引用。工作记录用日期与本次行为描述即可；需要时后续补充已存在提交的 hash。

## 提交消息格式

```text
<type>(<scope>): <具体行为>

说明触发条件、结果和必要取舍；简单变更可省略此段。

Task: NNN
Validation: 实际检查及结果；不能执行时说明原因
Cleanup: 删除项，或本次无废弃项
Compat: none，或例外标记、原因与清理任务
```

正文可中文，type/scope 用稳定简短英文。任务编号是格式占位，实际提交必须替换。多个任务写 `Task: NNN, MMM` 并解释不可分割性。详细验证证据可以引用 task 中对应记录，但不能只写“tested”。

| type | 用途 |
|---|---|
| feat | 新增可用能力 |
| fix | 修复行为错误 |
| refactor | 调整结构，保持对外行为；行为改变不能伪装成纯重构 |
| cleanup | 删除废弃实现、无用配置或资源 |
| build | 构建图、工具链、依赖及锁文件 |
| test | 测试与夹具 |
| docs | 文档与任务规划 |
| ci | 自动检查配置 |
| chore | 其他仓库维护，不能代替明确类型 |
| revert | 回退既有变更，说明目标和原因 |

scope 选择实际模块，如 `project`、`mesh`、`ffi`、`qml`、`docs`、`repo`。不使用“update”“misc”“WIP”作为行为描述。破坏既有接口/格式时标题冒号前加 `!`（如 `refactor(ffi)!:`），正文说明受影响调用方/数据和升级方法；不为避免标注破坏性变化而新增兼容层。

## 整理与回退

拆分、squash 或回退后，重新核对最终 commit 的代码、说明与 task 一致性。回退已完成能力时更新受影响任务和可用能力说明，不能仍标该能力有效完成；历史事实可保留在工作记录。

不为满足格式而擅自改写已有共享历史。写好规范或 task 不构成执行 commit、push、rebase 的请求；此类操作按当前实际工作指令执行。

# 代码清理与兼容例外规范

更新日期：2026-09-16。以下是项目强制约定，适用于自有代码、构建脚本、配置、资源和测试。

## 无死代码原则

Git 保存历史，当前仓库只保留当前支持行为所需的实现。替换或废弃功能时，在完成替换的同一 commit 删除旧实现及失效引用；不把清理默认推迟到以后。

必须一起检查并清理：

- 已无用途的函数、类型、模块、文件、导出与 import/include。
- 旧调用点、旧入口、重复分支、永远不成立的条件和失效 feature flag。
- 只服务于旧实现的依赖、构建 target、配置键、命令行选项和资源。
- 已失去验证对象的测试、夹具、示例、说明与注释。若测试仍验证受支持行为，应迁移到新实现，不能借清理删除有效覆盖。

不得使用注释块、`#if 0`、`old/`、`backup/`、`*_v1`、`*_legacy` 等方式保留废弃代码；不得通过 `allow(dead_code)`、`maybe_unused` 或 lint 排除让遗留实现继续存在。这些标识只是排查线索，不代表同名内容都可直接删除。

确实被 Qt 元对象/QML、FFI 导出、生成器或动态入口使用的代码，不因文本搜索不到调用点就视为死代码；必须有明确入口与必要验证。仍支持的平台实现和正在使用的库 adapter 也不是兼容遗留分支。局部搜索结合构建、注册、资源引用和测试确认可达性，不能自动批量删掉所有未命中符号。

## 不预留兼容代码

默认只实现明确选定的当前版本和行为。禁止为了猜测未来需求而添加向前兼容解析、字段猜测、静默忽略未知语义、降级 fallback、双版本分支或旧 API 别名；同样不默认保留向后兼容层。

遇到不支持的协议/schema/API，显式返回可定位错误，保留用户有效数据；不自动改写、尝试另一套含义或假装成功。版本检查与明确拒绝本身不是兼容层。

边界抽象、错误恢复和当前受支持平台的差异实现可正常存在，但不能借这些名称藏入旧版本兜底。需求确实要求兼容时才按下节登记；“以后可能用到”不构成必要性。

## 必要例外：统一标记

只有可具体说明的现实需求才可引入例外。在实现前写入所属 task 的“清理与兼容例外”章节，并在每个独立兼容入口紧邻位置使用统一标记：

```text
COMPAT(task NNN; remove-task MMM): 简述适用版本和必要原因
```

这是格式示意，NNN/MMM 必须替换为索引中真实任务编号，不能原样入代码。C++/Rust/QML 使用 `// COMPAT(...)`，CMake 使用 `# COMPAT(...)`；配置格式不允许注释时，在读取该配置的代码和 task 中标记。

紧邻标记或其 task 记录必须写清：

- 具体输入/API/依赖版本范围与触发条件。
- 为什么无法现在统一升级或移除，兼容期间的行为与失败方式。
- 责任维护者或模块、验证入口与覆盖样例。
- 可判断的删除条件，清理任务与目标版本或复查节点；不能只写“以后删除”。

兼容代码集中在最小 adapter/迁移入口，不扩散到业务核心。task 表明该例外是当前仍需要的行为，不是免于维护的旧实现。引入 task 可以在例外完整验证后 done；清理 task 必须保持可追踪状态，删除条件达成时立即移除兼容代码、标记与专用资源。

普通 TODO、FIXME、deprecated 注解或文件名不替代 COMPAT 标记。必要的版本 workaround 若承担兼容行为，也受本规范约束。

## 搜索与清理验收

从仓库根目录使用下列命令查找统一标记，结果包含规范示例，需区分说明文档和运行代码：

```sh
rg -n -F 'COMPAT(' .
```

对改动模块搜索旧符号、路径、配置键与依赖名，核对 CMake/QML/FFI 的注册入口。警告/静态分析是辅助证据，不是“没有死代码”的完整证明；不为通过检查而全局关闭告警。

每次提交在 task 记录本次删掉的内容，或说明未发生替换/无废弃项；兼容例外写“无”或逐项链接标记与清理任务。具体 commit 要求见 [提交规范](commits.md)。
